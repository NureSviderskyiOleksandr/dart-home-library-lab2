# Домашня бібліотека

Лабораторна робота 2 з дисципліни «Програмування мовою Dart» —
об’єктно-орієнтована модель предметної області.

- Виконав: Свідерський Олександр Геннадійович.
- Група: ПЗПІ-23-10.
- Номер у списку збірної групи: 16 (варіант 16 mod 15 = 1).
- Предметна область: домашня бібліотека.
- Код лабораторної роботи 1 — перший коміт репозиторію (тег `lab1`), ця робота — гілка `lab2`.

## Мета

Переробити програму лабораторної роботи 1 на бібліотеку класів: незмінний
клас-сутність із різними видами конструкторів, запечатану ієрархію станів,
домішки, методи розширення, узагальнене сховище, перелічення з членами,
записи й зіставлення зі зразком. Розбір, валідація й агрегування з ЛР 1
збережені, але працюють з об’єктами, а не із записами примітивів.

## Структура програми

| Файл | Вміст |
|---|---|
| `bin/home_library.dart` | Точка входу: один виклик `runApplication`. |
| `lib/home_library.dart` | Бібліотека-фасад, яка експортує решту файлів. |
| `lib/book.dart` | Клас `Book`, тип результату розбору, компаратори. |
| `lib/genre.dart` | Перелічення `Genre`. |
| `lib/reading_status.dart` | Запечатаний `ReadingStatus`, чотири підтипи, домішки. |
| `lib/identifiable.dart` | Інтерфейс `Identifiable`. |
| `lib/repository.dart` | Узагальнене сховище `Repository<T extends Identifiable>`. |
| `lib/extensions.dart` | Розширення `IsoDate` на `DateTime` і `PersonName` на `String`. |
| `lib/book_collection.dart` | Розширення `BookCollection` на `Iterable<Book>`, замикання-предикат. |
| `lib/library_report.dart` | Розбір набору рядків, опис стану, формування звіту. |
| `lib/sample_data.dart` | Демонстраційні вхідні рядки. |
| `test/home_library_test.dart` | Модульні тести (29). |
| `docs/` | Звіт і вивід `dart analyze` та `dart test`. |

Поділ `bin/` і `lib/` збережено з ЛР 1: точка входу не містить логіки, тому
модель можна використати в ЛР 3–4 і в тестах без запуску консольної програми.

Код розбито на файли за сутностями, а не залишено в одному файлі, як у ЛР 1:
кожен файл тепер описує один тип або одну групу операцій, і при читанні
коду не доводиться гортати 300 рядків, щоб знайти, наприклад, домішку.
Файли поки лежать безпосередньо в `lib/`; приховування реалізації в `lib/src/`
методичка передбачає з ЛР 4. Фасад `home_library.dart` дає один імпорт
`package:home_library/home_library.dart` для `bin/` і тестів. Альтернативою
була б одна бібліотека з `part`-файлами, але `part` об’єднує приватні члени
всіх файлів і заважає бачити, від чого залежить кожен файл.

Пакет перейменовано з `home_library_lab1` на `home_library`, бо проєкт
наскрізний і розвиватиметься до ЛР 4.

## Вибір типів даних

### Книга — незмінний клас `Book`

У ЛР 1 книга була іменованим записом. Запис не може мати іменованих
конструкторів, обчислюваних гетерів, методів і власної реалізації `==`,
тому тепер це клас. Усі поля `final`, конструктор константний: об’єкт
неможливо змінити після створення, тому його безпечно класти в `Set` і
використовувати як ключ `Map` — хеш-код не зміниться.

- Генеративний конструктор переписано на **первинний конструктор** Dart 3.13
  (`final class const Book({required final String author, ...})`). Клас
  скоротився з 216 до 208 рядків, і, головне, зник повтор: кожне поле раніше
  згадувалося двічі (оголошення й `this.поле` у конструкторі). Поведінка не
  змінилася: та сама сигнатура виклику, ті самі `final`-поля, конструктор
  лишився `const`, інваріанти `assert` перенесено з списку ініціалізації в
  тіло `this : ...`. Тести пройшли без змін.
- **`Book.fromCsv`** замінює функцію розбору з ЛР 1. Це фабричний, а не
  генеративний конструктор: генеративний конструктор не може «не створити»
  об’єкт, тому йому довелося б кидати виняток з середини списку
  ініціалізації. Для очікуваних помилок формату збережено статичний
  `Book.tryParse`, що повертає запис `(book, error)` без винятків, а
  `fromCsv` — тонка обгортка, яка кидає `FormatException`. Пара повторює
  `int.parse` / `int.tryParse` зі стандартної бібліотеки.
- **`Book.cached`** — фабричний конструктор із кешуванням: для однакового
  рядка повертає той самий екземпляр (`identical` → `true`). Кеш —
  приватне статичне поле `Map<String, Book>`.
- Обчислювані властивості: `id`, `isLong`, `century`, `pagesRead`.
- `==` і `hashCode` перевизначено разом через `Object.hash`. Експеримент:
  дві однакові книги у `Set` дають розмір 1; без `hashCode` — розмір 2,
  а аналізатор видає `hash_and_equals`. Пояснення: `HashSet` спершу
  порівнює хеш-коди, і два об’єкти з успадкованим від `Object` хешем
  потрапляють у різні кошики, тож `==` навіть не викликається.

### Жанр — перелічення `Genre`

Рядкове поле жанру замінено переліченням із полями `label`, `isFiction`,
константним конструктором, статичним `tryParse` і методом `describe`. Набір
жанрів скінченний, тому помилку в назві («кулінарія») тепер виявляє розбір,
а групування `Map<Genre, List<Book>>` не може утворити дві групи «роман» і
«Роман». Альтернатива — `const`-рядки жанрів — не дає перевірки компілятором.

### Стан читання — запечатаний клас `ReadingStatus`

Поле «дата прочитання» з ЛР 1 замінено станом, бо в реальній бібліотеці не
кожна книга вже прочитана:

| Підтип | Поле CSV | Дані |
|---|---|---|
| `Planned` | `в планах` | — |
| `Reading` | `читаю:412` | поточна сторінка |
| `Finished` | `2025-01-12` | дата прочитання |
| `Abandoned` | `кинуто:2025-09-01:95` | дата й сторінка |

Альтернативи: `DateTime?` (не відрізняє «у планах» від «кинуто»),
`enum` (значення не можуть мати різних полів), абстрактний клас (компілятор
не перевіряє вичерпність). `sealed` дає саме те, що треба: `switch` у
`describeStatus` без `default`, і після додавання четвертого підтипу
`Abandoned` аналізатор видав помилку:

```
error - lib/library_report.dart:38:7 - The type 'ReadingStatus' isn't
exhaustively matched by the switch cases since it doesn't match the pattern
'Abandoned()'. ... - non_exhaustive_switch_expression
```

Поліморфні члени: `label`, `completion(pageCount)`, `toCsvField()`.

### Домішки `DatedStatus` і `PageProgress`

Дата потрібна станам `Finished` і `Abandoned`, поточна сторінка — `Reading`
і `Abandoned`. Ці множини перетинаються лише в `Abandoned`, тому одиничне
успадкування їх не виражає: проміжний клас `DatedStatus extends
ReadingStatus` забрав би в `Abandoned` єдиний слот надкласу, і логіку
сторінок довелося б дублювати. Домішки додають поведінку класам із різних
гілок ієрархії незалежно одна від одної.

Обмеження `on ReadingProgress` робить дві речі: дозволяє підмішувати
домішку лише до станів читання і відкриває всередині домішки доступ до
`label` та `completion`. `PageProgress` навіть реалізує абстрактний метод
`completion` замість класу.

Під час роботи виявилося, що обмеження **не можна** записати як
`on ReadingStatus`: домішка сама стає прямим незапечатаним підтипом
запечатаного класу, і switch за чотирма підтипами перестає бути вичерпним
(помилка `... doesn't match the pattern 'DatedStatus()'`, не допомагає й
`base mixin`). Тому члени, потрібні домішкам, винесено в інтерфейс
`ReadingProgress`, який реалізує `ReadingStatus`.

### Узагальнене сховище `Repository<T extends Identifiable>`

Обмеження параметра типу гарантує, що в кожного `T` є гетер `id`, тому
сховище будує індекс `Map<String, T>` без зовнішньої функції-ключа і без
приведення типів. Без обмеження `T` був би для компілятора просто `Object?`,
і `item.id` не компілювався б. Тести використовують сховище з `Book` і з
тестовим класом `_Shelf`, що підтверджує повторне використання.

### Розширення

- `IsoDate` на `DateTime`: `toIsoDateString`, `daysUntil` і статичний
  `tryParseStrict`, який відкидає неіснуючі дати (`2025-02-30`), що
  `DateTime.tryParse` мовчки переносить на березень.
- `PersonName` на `String`: `isFullName`, `maskedName` (регулярний вираз з
  іменованими групами та `replaceAllMapped` з ЛР 1).
- `BookCollection` на `Iterable<Book>`: функції агрегування з ЛР 1 стали
  членами розширення (`books.totalPages`, `books.groupByGenre()`).
  Альтернатива — клас-обгортка `BookList` — вимагала б загортати кожен
  `List` і `Iterable`.

### Записи й зіставлення зі зразком

- `BookParseResult`, `BookListParseResult`, `PageStatistics` — записи для
  повернення кількох значень; на місці виклику вони деструктуруються:
  `final (:books, :errors) = parseBooks(lines);`.
- Охоронець `when`: `Finished(:final date) when date.year == referenceDate.year`
  у `describeStatus`, `PageProgress(:final currentPage) when currentPage > pageCount`
  у валідації.
- Розбір поля стану — switch за позиційним записом із null-check-зразками
  `(_, _, final finishedOn?, _, _) => Finished(finishedOn)`.

## Залежності

Залежностей часу виконання немає: усе реалізовано засобами `dart:core`.

| Пакет | Розділ | Навіщо | Альтернатива і чому не вона |
|---|---|---|---|
| `lints` | dev | набір правил `recommended` для `dart analyze` | вручну перелічувати правила — важче підтримувати |
| `test` | dev | модульні тести моделі | ручна перевірка через `dart run` не ловить регресій |

Розглядалися й не підключені:

- `equatable` — генерує `==`/`hashCode` за списком полів. Не підключено:
  робота прямо вимагає перевизначити `==` і `hashCode` вручну й поставити
  експеримент з їх видаленням.
- `freezed` / `built_value` — незмінні класи з `copyWith` через генерацію
  коду. Додають `build_runner` і згенеровані файли, а первинний конструктор
  вже прибирає основний повтор.
- `collection` — `groupBy`, `minBy`. `firstOrNull` уже є в `dart:core`
  з Dart 3.0, а групування — один `fold`.
- `meta` — анотація `@immutable`. Незмінність і так забезпечують
  `final`-поля та `const`-конструктор.

## Null safety: `!`, `late`, `dynamic`

Оператор `!`, ключове слово `late` і тип `dynamic` у коді й тестах не
використовуються. Місця, де вони могли б з’явитися, розв’язано інакше:

- `RegExpMatch.namedGroup` повертає `String?` — замість `!` використано
  `?? ''` і далі `tryParse`, тому пошкоджений рядок не спричиняє винятку.
- `Iterable.reduce` у `pageStatistics` викликається лише після перевірки
  `isEmpty`, а сама властивість повертає `PageStatistics?`.
- У тесті статистики замість `books.pageStatistics!` — `switch` з гілкою
  `case null: fail(...)`.
- Приведення `match as RegExpMatch` у `maskedName`: колбек
  `replaceAllMapped` отримує `Match`, але для `RegExp` це завжди
  `RegExpMatch`, а іменовані групи є лише в ньому.

## Порівняння з ЛР 1

| | ЛР 1 | ЛР 2 |
|---|---|---|
| Книга | запис `({String author, ...})` | клас `Book` з `==`, гетерами, методами |
| Жанр | `String` | `enum Genre` |
| Дата прочитання | `DateTime` | `sealed ReadingStatus` з 4 підтипами |
| Розбір | функція `parseBook` | `Book.tryParse` / `Book.fromCsv` / `Book.cached` |
| Валідація | функція `validateBook(book)` | метод `book.violations()` |
| Агрегування | функції над `Iterable<Book>` | розширення `BookCollection` |
| Зберігання | `List<Book>` | `Repository<Book>` з пошуком за `id` |
| Неіснуюча дата `2025-02-30` | приймалася | відхиляється |
